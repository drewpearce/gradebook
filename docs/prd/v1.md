# PRD — Gradebook v1

## Goal

A teacher-facing web app for recording student work and computing per-subject
grades. Real tool, intended to ship and be used. First user: a teacher running a
combined 1st/2nd grade class with multiple independently-graded subjects.

Vocabulary is defined in [CONTEXT.md](../../CONTEXT.md); architecture shape in
[ADR-0001](../adr/0001-spa-plus-json-api.md). This PRD does not redefine terms —
it uses them.

## Primary scenario

A single Class holds Students of more than one Grade Level (1st and 2nd). Each
Subject in the Class is graded independently, so a Student has a separate Grade
per Subject. An Assignment targets an Audience — 1st only, 2nd only, or both — and
a Student's Grade counts only the Assignments in their Audience.

## Product principles

- **Progressive disclosure.** Never force a choice that has only one option. A
  Class with one Subject never prompts for a subject; a Class with one Grade Level
  never prompts for an Audience. Adding a second Subject or Grade Level is what
  reveals those choices. When a Class gains its second Subject/Grade Level,
  existing Assignments are attributed to the original one.
- **The grade is always explainable.** A teacher should be able to see how any
  Grade was computed — which Assignments, which Category weights, what was counted.

## In scope (v1)

1. **Classes** — a Teacher creates and manages Classes; a Class has one or more
   Grade Levels.
2. **Students** — roster per Class; each Student has a Grade Level.
3. **Subjects** — one or more per Class, graded independently.
4. **Categories** — weighted Assignment groups per Subject (e.g. Homework 30%,
   Tests 70%).
5. **Assignments** — within a Subject and Category, with a max-points value and an
   Audience (grade-level-based).
6. **Scores** — enter a Student's points on an applicable Assignment.
7. **Grades** — computed per (Student, Subject): a percentage plus a Letter Grade
   from the Class's Grading Scale. Weighted categories, evaluated per-Student over
   their Audience.
8. **Auth** — single-Teacher login.

## Out of scope (v1)

Student logins, attendance, messaging/comments, LMS import/export, standards-based
grading, multi-term/semester rollover, multi-teacher/sharing.

## Grade computation

See [ADR-0002](../adr/0002-grade-computation-policy.md) for the full policy and
rejected alternatives. In summary, for a Student in a Subject:

- A Category's percentage is computed only over Assignments the Student has been
  **scored** on within their Audience; unscored applicable Assignments are
  excluded (not zero).
- If any weighted Category has no scored applicable Assignment for the Student, the
  Subject Grade is **Incomplete**.
- Otherwise, combine Categories by weight (weights sum to 100%, no re-scaling) and
  map the percentage to a Letter Grade via the Class's Grading Scale.

Grade computation is a pure function returning either a numeric Grade + Letter
Grade or Incomplete.

## Proposed build sequence (→ tickets)

1. Backend scaffold — FastAPI + SQLAlchemy + Postgres + migrations + CI (types,
   lint, tests).
2. Domain schema & migrations — Class, Grade Level, Student, Subject, Category,
   Assignment (with Audience), Score, Grading Scale.
3. Grade computation module — pure, tested against the mixed-audience scenario.
   (Gate on the two open questions.)
4. Core API — CRUD for the entities above + computed-grade endpoints.
5. Auth — single-teacher login.
6. Frontend scaffold — React + Vite + TanStack Query + typed API client from
   OpenAPI.
7. Roster & setup UI — classes, students, subjects, categories.
8. Assignment & score entry UI — grid entry, progressive disclosure of
   subject/audience.
9. Grades view — per-student, per-subject, with the explainable breakdown.
